Updated Technical Approach: Multi-Tenancy Support
Here are the key updates to the technical approach, woven into the existing sections.

1. Multi-Tenancy Architecture
A new guiding principle is the support for the bank's two distinct brands: "Digital Bank" and "General Bank".

Tenant Identification: The Vendor App is responsible for determining the user's brand/tenant context at the time of login (e.g., based on the URL, user profile, or selected brand). This tenantId (e.g., "digital" or "general") will be used to drive all subsequent logic.

Impacted Areas: Multi-tenancy affects four key areas:

Component Loading & Configuration (manifest.json)

Component Behavior & Styling (Props)

API Authentication & Authorization (JWT Claims)

Backend Business Logic (Data Scoping)

2. Updates to Build, Deployment, and Dependency Management
Manifest File (manifest.json): The manifest strategy will be adapted for multi-tenancy. Two primary options are:

Tenant-Specific Manifests (Recommended): The Vendor App fetches a manifest specific to the user's context (e.g., https://cdn.bank.com/digital/manifest.json or https://cdn.bank.com/general/manifest.json). This provides a clean separation of component versions, styles, and configurations per brand.

Single Unified Manifest: A single manifest contains entries for all tenants, structured to allow the Vendor App to select the appropriate component details based on the active tenantId.

Component Bundles: While some components might be shared between tenants, this approach allows for tenant-specific component bundles if functionality differs significantly (e.g., a component for the "General Bank" might include a "Find a Branch" feature not present in the "Digital Bank" version).

3. Updates to Communication Protocol
New Required Prop (brand): All Bank Components must accept a brand or tenantId prop. The Vendor App is responsible for passing the correct value (e.g., "digital" or "general") when rendering the component.

HTML

<bank-wire-transfer brand="digital" secure-token="..."></bank-wire-transfer>
Component Behavior: The Bank Component will use this brand prop to:

Apply Correct Theming: Use the prop to select brand-specific CSS classes for colors, fonts, and logos.

Conditional Rendering: Show or hide features based on the brand. For example, a "Schedule an Appointment" button would only render if brand="general".

4. Updates to Authentication and Authorization (JWS/JWE)
JWT Claims: The claims within the JWS payload must include a tenant_id claim.

Example Claim: "tenant_id": "digital"

The Vendor Backend is responsible for including the correct tenant_id in the JWT based on the user's context, which the Vendor Frontend should provide during the token request.

Bank's Backend API Validation:

When the Bank Backend decrypts the JWE and verifies the JWS, it must extract the tenant_id claim.

This claim is not optional; if it's missing or invalid, the request should be rejected.

All subsequent operations—database queries, business rule applications, and feature access—must be scoped to this tenant_id. This is a critical security measure to prevent data leakage between the two bank brands.

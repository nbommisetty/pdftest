6.5. Backend API (BFF) Data Architecture (NEWLY ADDED SECTION):
The BFF microservice utilizes a dual database strategy to manage its own state while interacting with the core tenant systems.

Private Micro DB: The BFF will have its own single, private database. This database is not for core customer data but for the BFF's operational needs, such as:

Configuration: Storing tenant-specific feature flags, UI settings, or endpoint mappings.

Caching: Caching non-sensitive, frequently accessed data to improve performance.

State Management: Handling state for multi-step operations.

All tables in this micro DB will be partitioned by a tenant_id column to keep its operational data segregated.

Tenant-Specific Persistent DBs: The primary role of the BFF is to connect to the correct system of record for each tenant.

The tenant_id extracted from the validated JWT acts as a routing key.

Based on this key, the BFF's internal logic will select the correct database connection string, credentials, and data access module for the specific tenant (e.g., the "Digital Bank DB" or the "General Bank DB").

This ensures all core business operations are automatically and securely scoped to the correct tenant's data, providing strong data isolation.
